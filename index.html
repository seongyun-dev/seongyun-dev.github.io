GitJobGITHUB × JOB MATCHING

2026.08.18 — 10.02 · 팀장

팀 프로젝트 우수상

사용자의 GitHub 저장소를 분석해 실제로 쓴 기술을 찾고, 채용공고의 기술 수요와 비교해 부족한 기술과 지원할 수 있는 공고를 보여주는 서비스입니다. 저는 팀장이자 Data Engineering 파트를 맡아, GitHub 활동 데이터와 채용공고 데이터를 모으고 처리하는 파이프라인을 만들었습니다.

담당
Kafka·Spark·HDFS 파이프라인, Redis 최적화, 모니터링
사용 기술
Kafka, Spark, HDFS, Redis, Prometheus, Grafana
저장소
github.com/seongyun-dev/GitJob ↗
  • 원본과 처리 결과를 나눠 저장했습니다

    대용량 원본은 HDFS에 그대로 두고, Spark로 처리한 결과는 Parquet 파일로 관리했습니다.

  • 작업마다 Kafka consumer를 따로 뒀습니다

    적재, 추출, 집계를 서로 다른 consumer가 맡게 해서 작업을 따로 돌리고, 필요하면 데이터를 다시 처리할 수 있게 했습니다.

  • 같은 코드는 두 번 분석하지 않게 했습니다

    repo_id + commit SHA를 키로 Redis에 분석 결과를 기록해 두고, 코드가 같을 때만 저장한 결과(Artifact)를 다시 썼습니다.

  • 파이프라인 상태를 Prometheus와 Grafana로 봤습니다

    서버 자원과 Kafka, HDFS 상태를 모니터링해서 파이프라인 어디가 이상한지 볼 수 있게 했습니다.

핵심 기여

Redis로 분석 결과를 재사용해 호출과 시간을 줄였습니다

  1. 현상

    같은 저장소를 분석할 때마다 근거를 처음부터 다시 확인하느라, GitHub API 호출이 많고 시간도 오래 걸렸습니다.

  2. 원인

    저장소 단위로만 재사용하는 방법(Repository-only)은 호출을 더 줄일 것처럼 보였지만, 같은 저장소라도 commit이 바뀌면 코드가 달라집니다. 예전 버전의 분석 결과가 그대로 나갈 위험이 있었습니다.

  3. 해결

    Redis 키를 repo_id + commit SHA로 잡아, 코드 버전이 같을 때만 저장해 둔 Artifact를 다시 썼습니다. 결과 파일과 조회용 인덱스는 따로 관리했습니다.

  4. 결과

    같은 저장소 묶음을 재사용 전후로 돌려 보니 GitHub API 호출이 2,971회에서 2,461회로 17.17%, 처리 시간이 1,125초에서 937초로 16.71% 줄었습니다.

02 / AI

RunWayAI RUNNING PACEMAKER

2026.10.06 — 11.18 · 팀원

진행 중

목표 거리와 완주 시간, 현재 심박수와 페이스, 코스 경사를 바탕으로 미래 심박수를 예측해 적정 페이스와 러닝 코스를 제안하는 러닝 페이스메이커입니다. 저는 AI 파트를 맡아 러닝 데이터를 전처리하고 미래 심박 예측 모델을 만들고 있고, OSM 도로 데이터와 직접 모은 러닝 GPX로 코스를 만들어 평가하는 로직을 설계하고 검증하고 있습니다. 지금은 실제 서비스에 쓰기 위해 개인화와 실시간 예측 구조를 다듬고 있습니다.

담당
러닝 데이터 수집·전처리, 미래 심박 예측 모델, 코스 생성·추천 로직
사용 기술
Python, NetworkX, GRU, Transformer
데이터
부산 OSM 도로 73,064 ways · 524,108 nodes, 국내 러닝 GPX 299개 (RunnerOn 34, 와리가리 265)
  • 러닝 데이터를 모으고 전처리했습니다

    코스 평가에 쓸 국내 러닝 GPX 299개를 모으고, 부산 OSM 도로 데이터를 코스 생성용 그래프로 만들었습니다. 심박 예측에 쓸 러닝 데이터도 전처리했습니다.

  • 심박이 늦게 반응하는 점을 고려해 모델을 비교했습니다

    심박수는 속도가 바뀐 뒤 조금 늦게 따라옵니다. 이 특성을 반영해 ODE 모델에서 시작해 GRU, Transformer 같은 시계열 모델까지 비교했습니다.

  • 정확도만 보고 모델을 고르지 않았습니다

    오차(MAE)가 가장 작은 모델(3.143 bpm)도 속도를 올렸을 때 심박이 내려간다고 예측하는 경우가 12% 있었습니다. 페이스를 제안하는 데 쓰는 예측이라 정확도와 함께 예측 방향도 보고, MAE 3.159 bpm에 거꾸로 된 예측 0.6%인 모델을 골랐습니다.

  • 팀원 모델을 같은 기준으로 비교하게 했습니다

    팀원들이 각자 만든 LightGBM, GRU, Transformer를 같은 데이터와 같은 평가 코드로 평가하도록 기준을 정했습니다. 30초, 60초, 2분 뒤 MAE의 평균을 기본 지표로 씁니다.

  • 코스 생성이 왜 느린지부터 확인했습니다

    단계별로 확인해 보니 그래프 객체를 만드는 데 시간이 가장 많이 들었습니다. 지도를 격자로 나눠 필요한 범위만 골라 그래프를 만드는 방식으로 바꿨습니다.

핵심 기여 1

느린 건 길찾기가 아니라 그래프 만드는 부분이었습니다

  1. 현상

    코스 추천 첫 요청이 5km는 3.72초, 10km는 12.92초 걸렸습니다.

  2. 원인

    단계별로 시간을 확인해 보니 그래프를 만드는 데 가장 오래 걸렸고, 그래프에 길을 하나씩 넣는 add_edge 호출만 37만 번쯤 됐습니다.

  3. 해결

    길찾기 방식은 그대로 두고 그래프 만드는 부분을 줄였습니다. 요청마다 처음부터 만들던 데이터는 한 번만 만들어 다시 쓰고, 지도를 격자로 나눠 요청한 범위에 걸리는 길만 골라 넣어 add_edge 호출을 줄였습니다. 겹치는 계산은 저장해 두고 다시 썼습니다.

  4. 검증

    빨라졌는데 추천이 바뀌면 의미가 없어서, 기존 방식과 10개 조건으로 비교했습니다. 만들어진 그래프와 경로, 전체 순위, 추천 TOP3가 모두 같았습니다.

  5. 결과

    그래프 만드는 단계만 보면 5km 2.13초 → 0.62초로 70.9%, 10km 8.32초 → 2.59초로 68.9% 줄었습니다. 첫 요청 전체 시간은 5km 3.72초 → 2.04초(45.2%), 10km 12.92초 → 8.08초(37.5%) 줄었습니다.

핵심 기여 2

평균은 가장 정확했지만, 가끔 거꾸로 예측했습니다

  1. 현상

    비교한 모델 중 평균 오차(MAE)가 3.143 bpm으로 가장 작은 모델도, 속도를 초속 0.5m 높여 보니 100번 중 12번꼴(12.0%)로 거꾸로 된 예측을 했습니다. 더 빨리 달리는데 심박은 내려간다고 예측한 것입니다.

  2. 원인

    이 예측은 사용자에게 페이스를 제안하는 데 씁니다. 속도가 빨라졌는데 심박 예측이 낮아지면, 사용자에게 맞지 않는 페이스를 제안할 수 있습니다. 평균 오차만 봐서는 이 문제가 드러나지 않았습니다.

  3. 해결

    Transformer 1개와 GRU 3개를 합친 모델을, 속도가 오르면 심박 예측도 오르도록 한 번 더 학습시켰습니다. Transformer 하나로 따로 시험했을 때도 거꾸로 된 예측이 11.5% → 1.7%로 줄었고, 평균 오차는 거의 그대로(+0.013 bpm)였습니다.

  4. 검증

    평균 오차와 거꾸로 된 예측 비율을 함께 비교했습니다. 거꾸로 된 예측은 "속도를 초속 0.5m 올렸는데 1분 뒤 심박이 내려간다고 예측한 경우"로 정해, 시험 데이터 전체에서 셌습니다. 2분 뒤 예측은 지금 심박을 그대로 쓰는 단순한 방법보다 오차가 1.64 bpm 작았습니다.

  5. 결과

    평균 오차는 3.143에서 3.159 bpm으로 거의 그대로(+0.016)였고, 거꾸로 된 예측은 12.0%에서 0.6%로 줄었습니다.
