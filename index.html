GitJobGITHUB × JOB MATCHING

2026.08.18 — 10.02 · 6인 팀 · 팀장

팀 프로젝트 우수상

사용자의 GitHub 저장소를 분석해 실제로 쓴 기술을 찾고, 채용공고의 기술 수요와 비교해 부족한 기술과 지원할 수 있는 공고를 보여 주는 서비스입니다. 팀장을 맡았고, 데이터 파이프라인 중 배치 처리(HDFS·Spark)와 GitHub 저장소 매핑을 담당했습니다.

  • Spark 집계

    6개월치 GH Archive 원본을 HDFS에 두고 Spark로 분산 집계해, 저장소 47,466,125개의 활동량을 Parquet으로 만들었습니다. 한 번 실행에 약 3시간 10분이 걸렸고, 주차별 활동량과 Top-N 집계도 따로 만들었습니다.

  • 실시간 경로 연결

    실시간 이벤트는 적재, 추출, 집계를 서로 다른 Kafka consumer가 맡는 팀 구조였고, consumer는 팀원들이 만들었습니다. 저는 그 출력을 배치 집계와 같은 형식으로 맞춰 주차별 집계에 합치고, Snapshot과 Checkpoint로 필요한 구간만 다시 처리할 수 있게 했습니다.

  • Artifact 재사용

    repo_id + commit SHA를 키로 Redis에 인덱스를 두고, 코드 버전이 같을 때만 따로 저장해 둔 분석 결과(Artifact)를 다시 썼습니다.

  • 모니터링

    Prometheus·Grafana로 서버 자원과 Kafka, HDFS 상태를 한 화면에서 확인했습니다.

핵심 기여 1

분석 결과 재사용 기준 정하기

  1. 현상

    같은 저장소를 분석할 때마다 기술 근거를 처음부터 다시 찾느라 GitHub API 호출이 많고 시간도 오래 걸렸습니다.

  2. 원인

    이미 분석한 결과를 다시 쓸 기준이 없었습니다. 저장소 단위로 재사용하면(Repository-only) 호출은 더 줄지만, commit이 바뀌어 코드가 달라져도 예전 분석 결과가 그대로 나갈 수 있었습니다.

  3. 해결

    재사용 기준을 저장소가 아니라 코드 버전으로 잡았습니다. repo_id + commit SHA가 모두 같을 때만 저장해 둔 Artifact를 다시 쓰고, Redis는 Artifact를 찾는 인덱스로만 썼습니다. 결과 파일은 별도 저장 공간에 두었습니다.

  4. 결과

    같은 저장소 묶음을 재사용 전후로 돌려 비교한 결과 GitHub API 호출이 2,971회에서 2,461회로 17.17% 줄었습니다. 처리 시간도 1,125초에서 937초로 줄었지만, Rate Limit 같은 외부 요인이 섞였을 수 있어 참고 수치로만 봅니다.

핵심 기여 2

backfill dry run 버그 수정

  1. 현상

    채용공고 분석 입력을 다시 채우는 backfill 도구는 기본이 dry run, 즉 무엇을 할지 계획만 보여 주고 아무것도 쓰지 않는 모드입니다. 그런데 같은 dry run을 다시 돌리면, 처음에 '이미 올라감'으로 나온 회차가 '체크포인트로 건너뜀'으로 바뀌어 나왔습니다.

  2. 원인

    이미 올라간 회차를 만나면 재개용 checkpoint 파일에 기록하는 코드가, dry run인지 확인하기 전에 실행되고 있었습니다. 계획을 읽기만 해도 재개 파일이 바뀌어서, 승인한 계획과 다음에 보는 계획이 달라졌습니다.

  3. 해결

    dry run일 때는 checkpoint를 기록하지 않도록 조건을 고쳤습니다. 실제 실행(--execute)에서는 그대로 기록해서, 중간에 멈춰도 이어서 처리할 수 있게 두었습니다.

  4. 결과

    dry run을 반복해도 checkpoint 파일이 바이트 단위로 같은지, dry run이 아무것도 올리지 않는지, 실제 실행은 여전히 기록하는지 테스트 6개로 확인했습니다.

RunWayAI RUNNING PACEMAKER

2026.10.06 — 11.18(예정) · 6인 팀 · 팀원

진행 중

목표 거리와 완주 시간, 현재 심박수와 페이스, 코스 경사로 앞으로의 심박수를 예측해 적정 페이스와 러닝 코스를 추천하는 서비스입니다. AI 파트에서 러닝 데이터 전처리, 심박 예측 모델, OSM 도로 데이터와 러닝 GPX를 이용한 코스 생성·평가 로직을 맡고 있습니다. 지금은 개인화와 실시간 예측 구조를 다듬는 중입니다.

담당
러닝 데이터 수집·전처리, 미래 심박 예측 모델, 코스 생성·추천 로직

  • 학습 데이터 검증

    사용자 단위로 학습·검증·시험 데이터를 나눠 같은 사람의 기록이 평가에 섞이지 않게 했습니다. GPS, 경사, 끊긴 시간 구간, 미래 시점 기록을 점검했고, 경사 값을 채워 넣었는지 표시하는 규칙에 어긋난 기록 295,746건을 0건으로 정리했습니다.

  • 모델 비교

    심박수는 속도가 바뀐 뒤 조금 늦게 따라옵니다. 이 특성을 반영할 수 있는 ODE 모델부터 GRU, Transformer 같은 시계열 모델까지 비교했습니다.

  • 예측 방향 평가

    오차가 가장 작은 모델도 속도를 올리면 심박이 내려간다고 예측하는 경우가 있었습니다. 페이스 추천에 쓰는 예측이라 예측 방향도 평가 기준에 넣어 모델을 다시 골랐습니다.

  • 공통 평가 기준

    팀원들이 각자 만든 LightGBM, GRU, Transformer를 같은 데이터와 같은 평가 코드로 평가하도록 기준을 정했습니다. 30초, 60초, 2분 뒤 MAE의 평균을 기본 지표로 씁니다.

  • 코스 생성 속도

    단계별 소요 시간을 측정해 보니 길찾기보다 그래프를 만드는 단계가 가장 오래 걸려, 이 부분을 줄였습니다.

핵심 기여 1

코스 추천 첫 응답 속도 개선

  1. 현상

    코스 추천 첫 요청이 5km는 3.72초, 10km는 12.92초 걸렸습니다.

  2. 원인

    단계별 소요 시간을 측정해 보니 그래프를 만드는 단계가 가장 오래 걸렸고, 그래프에 길을 하나씩 넣는 add_edge 호출이 약 37만 번이었습니다.

  3. 해결

    길찾기 방식은 그대로 두고 그래프 생성 단계만 줄였습니다. 요청마다 새로 만들던 데이터는 한 번만 만들어 재사용하고, 지도를 격자로 나눠 요청 범위에 걸리는 길만 넣어 add_edge 호출을 줄였습니다. 겹치는 계산 결과도 저장해 두고 다시 썼습니다.

  4. 검증

    기존 방식과 10개 조건으로 비교해 그래프, 경로, 전체 순위, 추천 TOP3가 모두 같은지 확인했습니다.

  5. 결과

    그래프 만드는 단계만 보면 5km 2.13초 → 0.62초로 70.9%, 10km 8.32초 → 2.59초로 68.9% 줄었습니다. 첫 요청 전체 시간은 5km 3.72초 → 2.04초(45.2%), 10km 12.92초 → 8.08초(37.5%) 줄었습니다.

핵심 기여 2

심박 예측 방향 오류 줄이기

  1. 현상

    비교한 모델 중 평균 오차(MAE)가 3.143 bpm으로 가장 낮은 모델도, 속도를 초속 0.5m 올렸을 때 100번 중 12번꼴(12.0%)로 거꾸로 된 예측을 했습니다. 더 빨리 달리는데 심박이 내려간다고 예측한 경우입니다.

  2. 원인

    MAE는 오차의 크기만 평균 내기 때문에, 속도를 바꿨을 때 예측이 맞는 방향으로 움직이는지는 알 수 없습니다. 이 예측은 페이스 추천에 쓰이므로 방향이 틀리면 맞지 않는 페이스를 추천하게 됩니다.

  3. 해결

    Transformer 1개와 GRU 3개를 합친 모델을 속도가 오르면 심박 예측도 오르도록 추가 학습했습니다. Transformer 하나로 따로 시험했을 때도 거꾸로 된 예측이 11.5% → 1.7%로 줄었고, MAE는 0.013 bpm 늘어난 정도였습니다.

  4. 검증

    거꾸로 된 예측은 "속도를 초속 0.5m 올렸는데 1분 뒤 심박이 내려간다고 예측한 경우"로 정하고, 시험 데이터 전체에서 MAE와 함께 비교했습니다. 2분 뒤 예측은 현재 심박을 그대로 쓰는 단순 기준보다 오차가 1.64 bpm 작았습니다.

  5. 결과

    MAE는 3.143에서 3.159 bpm으로 거의 같았고(+0.016), 거꾸로 된 예측은 12.0%에서 0.6%로 줄었습니다.
